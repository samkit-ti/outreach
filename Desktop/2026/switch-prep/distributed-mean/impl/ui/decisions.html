DM-001Who combines 20,000 partial results into one answer?

A partial result is C numbers — the same 8 MB object as an input file — so the “≤5 files at a time” limit binds combiners exactly as it binds readers.

Central accumulator REJECTED

Memory is fine — bandwidth is the objection: an Amdahl floor no worker count can lower. Also welds job state into one process’s RAM.

Two-phase barrier REJECTED

fast
med
slow
map phase | wall | reduce phase — striped = workers idle while finished partials sit untouchable

The slowest of 20,000 maps gates all merging, and 160 GB of partials must exist at once. Buys nothing: phase 2 still needs the same tree.

Column sharding REJECTEDKEPT AS ESCAPE HATCH

The constraint counts files, so slicing columns removes zero fan-in — pure added cost. Becomes the right second axis only if C grows past ~10⁸ (vector > worker RAM).

Pre-planned static tree REJECTED

Wiring merges to named children re-creates the barrier at every one of ~5,000 nodes. Its one prize — bit-identical reruns — is preserved as an opt-in flag.

Eager 5-ary tree through the queue CHOSEN

Σ,5Σ,5Σ,5 Σ,5Σ,5Σ,2 → pool of partials, each tagged with its file count
≥5 ready → merge oldest 5  ·  job quiet & ≥2 → drain (2–4)  ·  single & n=F → finalize
fast
slow
map and merge overlap — no wall anywhere; a straggler delays only its own 8 MB

Sums merge in any order, so whoever committed last pairs whatever is ready — the tree emerges, is never stored, and completion falls out of the counts (DM-003).

DM-002How does work meet workers of wildly different speeds?

The brief’s core scenario: heterogeneous workers, minimal idling.

Push — a speed-estimating scheduler REJECTED

scheduler
p̂: fast=1  med=2  slow=2 ← stale assigns shares ahead of time
fast
med
slow
forecast error = idle time — one wrong estimate nearly doubles the job (16 s vs ~8 s optimum)

Speed here is a noisy process (storage tails, cold caches, noisy neighbors) — history doesn’t predict it. Push’s one prize, data locality, is recoverable later as a claim-order hint.

Pull — workers claim when free CHOSEN

T7T8T9T10 ← one shared queue
fast ⟲ claims ×3 med ⟲ claims ×2 slow ⟲ claims ×1
self-balancing with zero estimation — a 3× faster worker simply asks 3× as often; a straggler’s blast radius is exactly one task, whatever F is

Greedy pull finishes within (ideal + one task) — the penalty is a constant, not a fraction of the job.

Chunk size — why 5 files per task

c=1 — fixed costs (8 MB partial + commit) dominate; 5× the tasks ✗
c=5 — overhead <1% of a 40 MB task ✓ (RAM cap binds here)
c=50 — slow worker’s one chunk sets the finish line ✗ + cap ✗
the formal optimum (√-rule) lands ≈32 → clamped to the cap; undershooting is cheap, overshooting is 50–150%

Per-task cost is O(C), not O(1) — every task writes a full 8 MB partial however few files it read. Amortize it; never exceed what the slowest can finish in time.

Drain mode — the tail patch CHOSEN

Σ,5Σ,5Σ,2 → strict “wait for 5” gate: 4th & 5th never come → stuck ∞
Σ,5Σ,5Σ,2 → job quiet? merge all 3 → Σ,12  (cost: ≤ ~7 extra merges, <0.15%)

Fires only when nothing else is running or pending — a bounded price for removing an unbounded stall. Correct at any size because partials carry counts.

Speculative duplicates (LATE-style) DEFERRED

R-lastheld by a slow-but-alive worker R-last′duplicate on a fast idle worker — first commit wins
already safe (deterministic keys + fenced commits) — but each duplicated leaf re-reads ~40 MB to save seconds

The only cure for slow-but-alive — adopted if p99 makespan exceeds 1.5× the throughput projection with a slow worker on the critical path. Trigger written in the record.

DM-003How does the system know a job is finished?

Hard here because merge tasks are created on the fly (no known total) and the queue redelivers (any signal built from events can fire twice).

Countdown counter REJECTED

remaining: 2→1→ 0 ← fires “done”!→ 1  (the merge that commit just spawned)
passes through zero legitimately between “last map done” and “its merge created” — result ships with unmerged partials. Redelivery adds double-decrements. Both fail silently.

Every safe-counter patch ends up consulting task state — at which point the counter is a cached copy of the truth, wired to the trigger. Demoted to the progress bar only.

Polling watcher REJECTEDKEPT AS SMOKE ALARM

Adds up to a poll interval of delay at the most visible moment, plus a process that needs its own health checks and single-instance election — to rediscover a fact the commit already knew.

“Queue is empty” REJECTED

queue: ∅ empty ≠ done — worker still holds the last task
and with concurrent jobs sharing the queue, “empty” says nothing about your job — and names no result

Racy alone, meaningless under multi-job concurrency, and even when true you still must find the answer — i.e., run the real check.

Conservation proof — count = F CHOSEN

Maps create counts, merges add them, consumption is exactly-once — so unmerged partials always partition the F files. Checking a fact twice is harmless; ticking a counter twice is corruption. Acting on it is a one-row CAS, so exactly one finalize ever exists.

DM-004Which queue technology?

The pairing step must atomically {mark ≤5 partials consumed + enqueue their merger}. That single requirement decides the technology.

External broker, order A: commit → send REJECTED

DB: partials consumed ✓ ① ② ✂ crash broker: merge task never sent
consumed partials, no merger, no retrigger — the job hangs silently forever

The failure the other write order can’t fix either →

External broker, order B: send → commit REJECTED

broker: merge task sent ✓ ① ② ✂ crash DB: partials NOT marked consumed
the same partials get merged again — sums counted twice, mean silently wrong

The standard fix — a transactional outbox — is a DB-backed queue you then also pay a broker to sit in front of.

Postgres SKIP LOCKED — the tasks table IS the queue CHOSEN

mark P1…P5 consumed+ INSERT merge task+ check count = F
ONE transaction — commits whole or not at all
load honesty: ~25k tasks/job at seconds each ⇒ ≪1k claims/s, against a pattern comfortable to ~1–10k/s. Leases are a column; fairness is an ORDER BY.

The dual-write class of bug is unrepresentable — state and queue share the commit.

SQS / managed broker DEFERRED — triggers written

switch when: sustained > 5k tasks/s · cross-region consumers · multi-service fan-out → SQS behind the QueueAdapter seam, + transactional outbox
respected, not dismissed: managed, unbounded, built-in DLQs — just not what this correctness spine needs

Also structurally: an 8 MB partial exceeds its 256 KB message cap 32× — the queue could never carry data here anyway (see DM-005).

DM-005Where do the bytes live, and in what format?

Coat-check: queue carries tickets, store carries bytes CHOSEN

queue msg: s3://…/M1.f64 (<1 KB) ↔ object store: 8 MB partials, 800 GB inputs
8 MB into a 256 KB message = 32× over — references or nothing. Control plane : data plane ≈ 1 : 50,000 by bytes.

MinIO locally, S3 in the cloud — same code path. Node-owned inputs are read-only behind an allow-list.

Format: raw float64 vs CSV

.f64 — 8 MB, zero parsing (both languages read it directly) ✓ intermediates
CSV — ~20 MB (2.5×) + parse cost kept for inputs & the human-readable result

No human ever reads an intermediate file — don’t pay text costs on 200 GB of them.

Result delivery 302 → pre-signed URL

clientGET /result → API: 302 (15-min signed link)→ store serves the bytes
the API never touches result bytes — it stays a pure control plane (`?inline=1` proxies, for curl)

Rejected: API streaming every download (20 MB bodies through the control plane), and webhooks (no authenticated callee).

DM-006Workers crash, stall, and run tasks twice. Why is the answer still exact?

Lease · heartbeat · deadline CHOSEN

Liveness never depends on a worker’s self-report.

Retries made harmless, not impossible CHOSEN

retry writes …/M1.f64 again → identical bytes, same name: overwrites itself ✓
zombie’s late commit (old token) → WHERE lease_token = mine … 0 rows → discarded
plus: at most one partial per task (unique), and a merge’s inputs are frozen at its creation

Exactly-once across a queue and an object store doesn’t exist; at-least-once + idempotent effects is outcome-equivalent — and buildable.

Rejected shapes

✗ at-most-once — silently loses crashed work
✗ two-phase commit / “exactly-once” — can’t cover the object store; pays latency chasing a myth
✗ ZooKeeper/etcd membership — a second stateful system for what a column does

Failure handling here is columns and conditions inside transactions that already exist.

DM-007A big job is running and a small one arrives. Who gets the workers?

Strict FIFO REJECTED

J1J1J1J1 J1…×25,000 J2J2J2
the 3-task job waits hours for ~15 s of work — and adding workers speeds the convoy, never reorders it

Head-of-line blocking is a policy failure, not a capacity failure.

Least-served job first (one ORDER BY) CHOSEN

J2J1J2J1 J2J1J1
claim ORDER BY (job’s in-flight count ASC, priority ASC, age) — finalize=0 < reduce=1 < map=2
small job finishes in ~its own work time; the big job loses ~0.01%

Possible only because the queue is a table (DM-004). Rejected alongside: per-job queues + a dispatcher component (moving parts for what one clause does); weighted fair queuing (deferred — no tenants yet).

DM-008How is the worker count W controlled through the API?

Thermostat: desired-state + reconciler CHOSEN

API writes desired: 8 → supervisor loop: compare & converge → start/stop workers (compose locally, ECS in cloud — same loop)
scale-down is polite (finish task → exit) but never load-bearing — the lease is the backstop

One process per worker: a fault costs one lease, and W stays a single number.

Rejected shapes

✗ API spawns processes itself — the control plane becomes a stateful babysitter
✗ workers manage their own population — who starts the first one? who wins a scale-down race?
◌ queue-depth autoscaling — DEFERRED: the requirement is user-set W

Same pattern as everything else: write the wish somewhere durable; let a loop make it true.

computed from partial rows (state, monotone by construction). Stream: append-only events over SSE, tail reads 1 s behind commit — ids are assigned in order but become visible in commit order; the lag is the no-skip guarantee.

DM-010Did distributing the sum cost any accuracy?

Worst-case rounding error at F = 100,000 float64 + tree

naive serial loop ≈ 1.1e-11
our 5-ary tree ≈ 8.9e-16
numpy (pairwise) ≈ same
log scale in spirit: ~10,000× apart. The tree IS pairwise summation — the accuracy is free, a side-effect of the shape the RAM constraint forced.

The honest claim: distribution is accuracy-neutral versus a good single-node implementation; only a hand-written naive loop loses. Kahan compensation: DEFERRED — doubles partial size to win a digit these bounds don’t need. Values ∈ float64 with 2⁵³ headroom — no overflow.

DM-011Why build this at all, instead of adopting an engine?

Spark / Dask REJECTED HERE

computes this in ~6 lines (treeAggregate) — but erases the deliverable (the orchestration algorithm itself), and assumes homogeneous, co-scheduled executors — the assumption this problem withdraws. Absent these constraints, it wins — said openly.

Right tool, wrong constraints.

Temporal / Step Functions REJECTED

~25k activities per job strains history-per-workflow models, and the load-bearing invariant (consume-partials + enqueue-merger, atomically) lives outside their transaction boundary — you’d still need the Postgres transaction, now coordinated with a second stateful system.

The dual-write DM-004 exists to kill, reintroduced at the platform level.

Celery / RQ / Ray REJECTED

chord-style fan-in is the counter design DM-003 rejects; broker↔DB is the dual write again; a TypeScript producer is a second-class citizen in the protocol.

Inherits both core objections at once.

Build on primitives CHOSEN

the components are fixed (Node API · DB · any queue · Python workers) and every distinctive mechanism here — the eager tree, the count-proof, fairness-as-ORDER-BY — exists because the state and the queue share one transaction. Five containers; smaller than any engine’s control plane.

The honest cost is owning the failure modes — priced in DM-006.
